Performance Testing
===================

The project ships a suite of Python tools under ``tools/`` for
measuring, recording, and analysing the language server's
performance. They share a common *session file* format — a JSON
array of LSP messages that is replayed against the server — produced
by :ref:`lsp_perf_session` or :ref:`lsp_log_parse` and consumed by
:ref:`lsp_bench`, :ref:`lsp_record_bench`, and :ref:`callgrind`.

Pipeline overview
-----------------

The benchmarking tools form a pipeline that takes a synthetic or
real-world TaskJuggler project and produces comparable timing
records::

   generate_large_tjp.py               (one-time) create fixture .tjp files
       |
       v
   lsp_perf_session.py                 build session JSON from a .tjp file
       |                               (pre-built session files are committed
       v                                under test/session_*.json)
   lsp_bench.py / lsp_record_bench.py  replay session, collect timings
       |
       v
   lsp_check_perf.py                   compare records, flag regressions

Typical usage is to run the recorder, then the comparison check::

   # Record a full benchmark run across all fixtures (appends to benchmarks.jsonl):
   python3 tools/lsp_record_bench.py

   # Compare the last two records and flag regressions:
   python3 tools/lsp_check_perf.py

   # Run a single fixture manually with timing output:
   python3 tools/lsp_bench.py ./taskjuggler-lsp test/session_flat.json

   # Quick ad-hoc timing run against a TJP file:
   python3 tools/lsp_perf_session.py test/perf_flat.tjp --run ./taskjuggler-lsp

Fixtures
--------

TJP files (``test/perf_*.tjp``)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The committed ``test/perf_*.tjp`` files are large, valid TaskJuggler
projects generated by ``generate_large_tjp.py``. Each fixture covers
a different structural stress profile so that regressions in one code
path show up regardless of how the file happens to be shaped.

.. list-table::
   :header-rows: 1
   :widths: 22 38 40

   * - File
     - Structure
     - Purpose
   * - ``perf_flat.tjp``
     - 10k tasks, depth=1, 2.0 deps/task
     - Widest file; exercises linear token scans
   * - ``perf_wide.tjp``
     - 10k tasks, depth=2, 2.0 deps/task
     - Shallow group hierarchy
   * - ``perf_balanced.tjp``
     - 10k tasks, depth=3, 2.0 deps/task
     - Baseline balanced tree
   * - ``perf_highdeps.tjp``
     - 10k tasks, depth=3, 8.0 deps/task
     - Stresses dep-ref validation
   * - ``perf_deep.tjp``
     - 10k tasks, depth=6, 2.0 deps/task
     - Deeply nested; stresses ``scan_kw_stack``

To regenerate any of them::

   python3 tools/generate_large_tjp.py --tasks 10000 --depth 1 --deps-per-task 2 \
       --output test/perf_flat.tjp
   python3 tools/generate_large_tjp.py --tasks 2000 --depth 3 --deps-per-task 8 \
       --output test/perf_highdeps.tjp

Session files (``test/session_*.json``)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Each TJP fixture has a pre-built JSON message sequence committed
alongside it. Two variants per fixture are kept under version
control: a standard run and a ``_warm`` run that issues a
``didChange`` notification before requesting handlers, exercising the
re-parse path::

   test/session_{flat,wide,balanced,highdeps,deep}.json
   test/session_{flat,wide,balanced,highdeps,deep}_warm.json

To regenerate a session file from its TJP fixture::

   python3 tools/lsp_perf_session.py test/perf_flat.tjp \
       --output test/session_flat.json

Tools
-----

.. _generate_large_tjp:

generate_large_tjp.py
~~~~~~~~~~~~~~~~~~~~~

Generates a large, valid ``.tjp`` file by emitting a synthetic task
tree with deterministic IDs and a (configurable) density of
``depends`` references. Output is acyclic: every dep target was
declared earlier in the file.

Key options:

``--tasks N``
   Total number of leaf tasks (default: 1000).

``--depth N``
   Nesting depth of the task hierarchy (1 = flat, no groups).

``--deps-per-task N``
   Average ``depends`` references per task. May be fractional.

``--output FILE``
   Destination file. Defaults to stdout.

.. _lsp_perf_session:

lsp_perf_session.py
~~~~~~~~~~~~~~~~~~~

Builds a realistic LSP session — initialize, didOpen, a mix of
requests, shutdown — from a ``.tjp`` file. Cursor positions are
sampled so that each handler exercises its interesting code paths
(hover lands on documented keyword tokens; completion samples a
weighted mix of keyword, dep-ref, resource-ref, and account-ref
positions; definition / references land on positions that return
non-null results).

Request types selectable through ``--requests``: ``hover``,
``completion``, ``signature``, ``definition``, ``references``,
``document-symbol``, ``folding-range``, ``semantic-tokens``,
``workspace-symbol``, ``didchange``.

::

   # Write a session file for later replay:
   python3 tools/lsp_perf_session.py test/perf_flat.tjp \
       --output test/session_flat.json

   # Quick single-shot run with timing output (no file written):
   python3 tools/lsp_perf_session.py test/perf_flat.tjp \
       --run ./taskjuggler-lsp

   # Focus on one method with more sample positions:
   python3 tools/lsp_perf_session.py test/perf_flat.tjp \
       --requests completion --positions 10 --run ./taskjuggler-lsp

.. _lsp_log_parse:

lsp_log_parse.py
~~~~~~~~~~~~~~~~

Converts an Emacs ``lsp-mode`` trace log into a session JSON file
compatible with :ref:`lsp_bench` and :ref:`callgrind`. Enable
``lsp-log-io`` in Emacs (``M-x lsp-workspace-set-log-level RET io``),
reproduce the scenario, export the log buffer, then parse it::

   python3 tools/lsp_log_parse.py /path/to/lsp-log.txt -o session.json

Only outgoing (client to server) messages are kept; server responses
and server-initiated notifications are dropped.

.. _lsp_bench:

lsp_bench.py
~~~~~~~~~~~~

Replays a session file against a server binary across multiple
iterations and reports per-method ``n``, mean, median, min, max, and
p95 (when at least 20 samples are collected). Notifications are
fire-and-forget; requests block until the matching response arrives,
so each round-trip is timed individually.

::

   python3 tools/lsp_bench.py ./taskjuggler-lsp test/session_flat.json \
       --iterations 7 --warmup 2

   # Record a single run under Linux perf:
   python3 tools/lsp_bench.py ./taskjuggler-lsp test/session_flat.json \
       --perf perf.data

.. _lsp_record_bench:

lsp_record_bench.py
~~~~~~~~~~~~~~~~~~~

Runs every ``test/session_*.json`` and ``test/session_*_warm.json``
fixture through ``lsp_bench``'s core, then appends a single JSON line
to ``benchmarks.jsonl``. The line records the git commit hash, an
ISO-8601 timestamp, the hostname, and per-method, per-fixture
statistics::

   python3 tools/lsp_record_bench.py
   python3 tools/lsp_record_bench.py --iterations 10 --warmup 3
   python3 tools/lsp_record_bench.py --dry-run   # print without writing

Methods treated as whole-document (one sample per run) are
``textDocument/semanticTokens/full``, ``textDocument/documentSymbol``,
and ``textDocument/foldingRange``. Every other method records one
sample per cursor position.

.. _lsp_check_perf:

lsp_check_perf.py
~~~~~~~~~~~~~~~~~

Compares the two most recent records in ``benchmarks.jsonl`` and
flags any (fixture, method) pair whose timing regressed beyond a
percentage threshold. Exits ``0`` when nothing regresses and ``1``
otherwise, so it can be wired straight into CI::

   python3 tools/lsp_check_perf.py                       # default 10% threshold
   python3 tools/lsp_check_perf.py --threshold 5         # stricter
   python3 tools/lsp_check_perf.py --method documentSymbol --fixture flat
   python3 tools/lsp_check_perf.py --threshold 999       # print table, never fail

.. _callgrind:

callgrind.py
~~~~~~~~~~~~

Profiles a scenario under Valgrind Callgrind, or analyses an existing
output file. The two modes are selected by the input file
extension: ``.json`` triggers profile mode, ``.out`` triggers parse
mode.

Profile mode requires a debug build (``make debug``) so that function
names resolve. Callgrind itself runs roughly twenty times slower than
a normal execution, so prefer a focused scenario with a small number
of positions and repetitions::

   make debug   # build taskjuggler-lsp-debug with -g symbols

   # Generate a focused scenario (initialize + initialized + didOpen + one request):
   python3 tools/lsp_perf_session.py test/perf_flat.tjp \
       --requests completion --positions 1 --repeat 1 \
       --output /tmp/flat_completion.json

   # Profile it:
   python3 tools/callgrind.py ./taskjuggler-lsp-debug \
       /tmp/flat_completion.json \
       -o test/callgrind/flat_completion/

   # Analyse a previously recorded output file:
   python3 tools/callgrind.py test/callgrind/flat_completion/callgrind.out --top 30
   python3 tools/callgrind.py test/callgrind/flat_completion/callgrind.out \
       --tree handle_completion

Profile mode writes ``callgrind.out`` and ``calltree.txt`` to the
output directory and then prints a flat top-N and a call tree. Parse
mode reads an existing ``callgrind.out`` directly and prints the same
analysis. The output directory can also be opened in KCachegrind for
interactive exploration.
